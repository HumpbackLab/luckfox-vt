# ipc_lite H.264 实机调查记录

日期：2026-04-13

## 1. 范围

本轮调查只针对当前仓库 `project/app/ipc_lite/` 的 `H.264` 路径，且使用实际硬件：

- 板型：Luckfox Pico / RV1106
- 传感器：`mis5001`
- 工作路径：`/root/ipc_lite`
- 当前保守分辨率：`704x576`
- 输入路径：`vi_channel = 1`，即 `rkisp_selfpath`

目标不是单纯确认 `RTSP` 控制面是否可连，而是确认：

1. `H.264` 是否真实出有效视频数据
2. 是否存在“能握手但实际黑屏”的假流
3. 码率配置是否真实生效

## 2. 本轮实测结论

### 2.1 H.264 不是“始终黑屏”

重新冷启动后，`H.264` 在至少一部分运行窗口内可以正常出画：

- 主机侧 `ffplay` 可持续显示正常视频
- 板端初期 `stats` 可见：
  - `fps` 约 `24-26`
  - `kbps` 约 `80-125`
  - `last_len` 不再固定为 `26`
- 抓下来的原始 `H.264` 文件经 `ffprobe/ffmpeg` 可正常识别和解码

这说明当前 `H.264` 路径不是“启动即坏”。

### 2.2 但 H.264 存在明显状态性退化

本轮同样复现了另一种状态：`RTSP` 仍然能握手，但实际数据面退化为极低码率的小包流：

- `fps` 仍维持在 `22-25`
- `kbps` 下降到 `5-6`
- `last_len` 长时间固定在 `26`
- 主机侧 `ffplay` 可能表现为黑屏或几乎无有效画面

这类状态下，不能再把流视为“正常视频流”。

结论应表述为：

- `ipc_lite H.264` 当前是“间歇可用”
- 不是“稳定正常”

### 2.3 黑屏问题确实存在，但不是必现

本轮出现了两种实际状态：

1. 冷启动后一段时间内可正常出画
2. 某些运行窗口退化为 `26B` 小包流，主机端表现为黑屏或近似黑屏

因此黑屏现象是真实问题，但不是每次启动都立即出现。

## 3. 关键实测现象

### 3.1 冷启动后可正常出画

在一次 fresh restart 后：

- 板端 `stats` 曾达到：
  - `frames=1772`
  - `bytes=938922`
  - `fps=23.46`
  - `kbps=80.69`
  - `last_len=71`
- 更早的若干统计区间也出现过：
  - `kbps=117.44`
  - `kbps=125.89`
  - `kbps=128.16`

这说明 `H.264` 在当前保守分辨率下并非完全不工作。

### 3.2 退化状态下的典型特征

另一轮长时间运行中，板端日志稳定出现：

- `kbps` 只有 `5-6`
- `last_len = 26`

典型样例：

- `frames=10854 bytes=338253 fps=23.47 kbps=5.44 last_len=26`
- `frames=10904 bytes=339694 fps=24.97 kbps=5.76 last_len=26`

这类数据和用户主机侧 `ffplay` 黑屏现象是相互吻合的。

### 3.3 黑帧并非整段持续

对一段可解码的 `H.264` 码流做了简单亮度统计：

- 启动极早期存在黑帧
- 但后续抽样帧 `YAVG` 约 `78`

因此“全程纯黑”的说法不准确，更接近：

- 启动初期可能有黑帧
- 正常状态下后续画面是有效的
- 退化状态下则可能回到用户可见的黑屏/无有效画面

## 4. 高码率测试结果

本轮在固定 `704x576 + H.264` 下测试了四档 `bitrate_kbps`：

### 4.1 结果汇总

| 配置码率 | 板端最终 `remote_kbps` | `last_len` | 原始文件平均码率 | 结论 |
|---|---:|---:|---:|---|
| `512`  | `5.55`   | `26` | `25.76`  | 退化 |
| `1024` | `5.86`   | `26` | `33.55`  | 退化 |
| `1536` | `128.16` | `38` | `144.85` | 相对最好，但远低于配置 |
| `2048` | `5.24`   | `26` | `25.94`  | 退化 |

### 4.2 结论

单纯提高 `bitrate_kbps` 并不能稳定解决问题：

- `512 / 1024 / 2048` 三档都掉进了同一类退化状态
- `1536` 是本轮唯一相对可用的一档
- 但即便 `1536`，实际也只有约 `128-145 kbps`

这说明：

1. 当前 `H.264` 的码率配置没有被稳定兑现
2. 问题不是“码率太低所以看不到”，而是“编码路径会状态性退化”

## 5. 代码侧关注点

本轮未修改仓库代码，但确认了当前实现的主要落点：

- `codec` 解析：
  - `project/app/ipc_lite/src/config.c`
- `H.264` RC 与 profile 初始化：
  - `project/app/ipc_lite/src/mpi_pipeline.c`
- `H.264` 专用 defaults：
  - `apply_h264_defaults()`
- `RTSP` 对 `H.264/H.265` 的 codec 选择：
  - `project/app/ipc_lite/src/rtsp_sink.c`

本轮结果说明，当前问题更像是：

- `H.264` 路径虽然接通
- 但码率控制或编码输出状态不稳定
- 最终表现为“有时可用，有时退化成极小包流”

## 6. 建议的下一步

本轮不建议立即上更高分辨率。

建议优先顺序如下：

### 6.1 固定当前保守分辨率

先固定：

- `704x576`
- `H.264`
- `vi_channel = 1`

原因：

- 当前问题核心仍在 `H.264` 编码稳定性
- 若此时再叠加更高分辨率，会把 CSI/VI/VENC 三类问题混在一起

### 6.2 优先复测 `1536 kbps + gop=25`

本轮 `1536 kbps` 是唯一相对有希望的档位。

建议下一步先试：

- `bitrate_kbps = 1536`
- `gop = 25`

目标是看：

1. 是否还能维持非 `26B` 小包状态
2. `ffplay` 的卡顿/恢复是否改善
3. 板端 `remote_kbps` 是否更稳定

### 6.3 若仍退化，再深入查 H.264 输出路径

若 `1536 + gop=25` 仍会退化，应直接收敛代码，而不是继续扫更多参数：

- 检查 `H.264` RC 参数是否真实被底层接受
- 检查 `apply_h264_defaults()` 是否引入了不利于当前板端的组合
- 检查 `RK_MPI_VENC_GetStream()` 取到的小包是否是编码器异常状态，而非正常 slice

## 7. 本轮结论摘要

一句话总结：

- 当前仓库的 `ipc_lite H.264` 不是“完全不工作”，但也绝不能称为“已经稳定正常”

更准确的状态是：

- 冷启动后有机会正常出画
- 但存在明显的状态性退化
- 提高码率不是稳定解法
- 当前最值得继续试的是：
  - `704x576 + H.264 + 1536 kbps + gop=25`

## 8. 追加调查：短跑复现把问题进一步收敛

后续继续用实机做了更可重复的短跑测试：

- 固定 `704x576 + selfpath + file-only`
- 每轮运行约 `8s`
- 每轮开始前都清理上一次 `ipc_lite`
- 每轮都单独观察：
  - 板端 `stats`
  - 输出文件大小
  - 同时间段 `dmesg`

这样做的目的，是把“偶发退化”从单次主观观察，变成可统计的现象。

### 8.1 追加前的 H.264 复现结果

在未继续改 `isp.c` 前，连续做了 `6` 次 `H.264 512 kbps` 短跑：

- `5/6` 次落在约 `100-126 kbps`
- `1/6` 次直接掉进退化态：
  - `kbps = 5.03`
  - `last_len = 26`
  - 输出文件仅约 `32 KB`

最关键的是：

- 这 `6` 次里，每次启动时都出现了同类底层错误：
  - `mipi-csi2-hw ERR1:0x10`
  - `rkcif-mipi-lvds: ERROR: csi size err`
  - `rkisp-vir0: CIF_ISP_PIC_SIZE_ERROR`

因此可以确认：

- `csi size err / PIC_SIZE_ERROR` 是稳定存在的背景问题
- 但它本身不足以解释为什么 `H.264` 只在部分轮次退化成 `26B` 小包

### 8.2 追加前的 H.265 对照结果

同样方法下，`H.265 512 kbps` 也做了 `6` 次短跑。

结果并不健康：

- 部分轮次只有 `6.x kbps`
- `last_len` 长时间固定在 `31`
- 也有部分轮次可到约 `60-78 kbps`

这说明：

1. 当前问题并不只属于 `H.264`
2. 板级 `sensor/CSI/ISP` 背景异常会同时影响 `H.264/H.265`
3. 但 `H.264` 的异常表现更显眼，因为它更容易在用户侧表现为 `26B` 小包黑屏

## 9. 代码对照后发现的新线索

继续对照 `rkipc rv1106_ipc` 后，发现 `ipc_lite` 的 AIQ 启动路径比 `rkipc` 少了两步关键 pre-init：

1. `rk_aiq_uapi2_sysctl_preInit_devBufCnt(sensor, "rkraw_rx", 2)`
2. `rk_aiq_uapi2_sysctl_preInit_scene(sensor, "normal", "day")`

同时，`ipc_lite` 原先使用的是：

- `rk_aiq_uapi2_sysctl_enumStaticMetas()`

而 `rkipc rv1106` 使用的是：

- `rk_aiq_uapi2_sysctl_enumStaticMetasByPhyId()`

这说明 `ipc_lite` 的 AIQ 初始化确实比 `rkipc` 更“薄”，并非完全等价。

## 10. 试验性修正与结果

### 10.1 本轮新增代码改动

本轮在 `project/app/ipc_lite/src/isp.c` 做了试验性收敛：

- 改用 `rk_aiq_uapi2_sysctl_enumStaticMetasByPhyId()`
- 补上 `preInit_devBufCnt(sensor, "rkraw_rx", 2)`
- 补上 `preInit_scene(sensor, "normal", "day")`

这是一次“向 `rkipc` AIQ 初始化靠拢”的针对性试验。

### 10.2 修正后的 H.264 复测结果

把新二进制重新部署到板上后，再次做 `6` 次 `H.264 512 kbps` 短跑：

- `6/6` 次都没有再掉进 `5 kbps / 26B` 退化态
- `6/6` 次都稳定在约 `98-115 kbps`
- 但每次启动时仍然继续出现：
  - `ERR1:0x10`
  - `csi size err`
  - `PIC_SIZE_ERROR`

这组结果很重要，因为它说明：

- 本轮补上的 AIQ pre-init，并没有消除底层 `CSI/ISP` 错误
- 但它明显降低了 `H.264` 掉进“极小包退化态”的概率

可以更直接地表述为：

- `H.264` 的异常，不是单纯由 `csi size err` 直接决定
- `ipc_lite` 原先偏薄的 AIQ 初始化，会放大 `H.264` 进入坏状态的概率

### 10.3 修正后的 H.265 复测结果

同样补丁下，`H.265 512 kbps` 再做 `6` 次短跑，仍然能看到明显退化：

- 多轮仍在 `6.x kbps`
- `last_len` 长时间固定在 `31`
- 也有少数轮次可回到约 `72-79 kbps`

这说明本轮改动的作用边界也很清楚：

- 它对 `H.264` 的状态性退化有明显改善
- 但并没有从根上解决板级输入链路不稳

## 11. 追加后的结论

截至本轮，问题应拆成两层：

### 11.1 已确认的 `ipc_lite` 侧问题

`ipc_lite` 原先 AIQ 初始化过于简化，缺少与 `rkipc` 对齐的 pre-init。

这个缺口会显著增加 `H.264` 掉进：

- `5 kbps`
- `last_len = 26`
- 主机侧黑屏/近黑屏

这类坏状态的概率。

也就是说：

- `H.264` “不正常”并不只是底层板级问题
- `ipc_lite` 自身的 AIQ 初始化差异，确实是一个可验证的促发因素

### 11.2 仍然存在的板级问题

即使补完上述 AIQ pre-init：

- `mipi-csi2-hw ERR1:0x10`
- `csi size err`
- `PIC_SIZE_ERROR`

仍然在每次测试时持续存在。

同时 `H.265` 仍会明显掉码，说明：

- 当前板级 `sensor/CSI/ISP` 链路依旧不干净
- 码率长期远低于配置值的问题，还不能只靠 `ipc_lite` 层修完

## 12. 下一步建议更新

原先“继续扫 `H.264 bitrate/gop` 参数”的优先级应下调。

更合理的顺序应改为：

1. 先保留本轮 `isp.c` 修正，继续确认 `H.264 RTSP` 长时播放是否同步改善
2. 把 `H.264` 视为“已部分收敛”，不要再把主要精力放在 `RC/profile` 细调上
3. 转而继续追 `sensor/CSI/ISP` 启动异常，尤其是：
   - `fs/fe mis`
   - `csi size err`
   - `PIC_SIZE_ERROR`
4. 若后续需要继续比对，优先对照：
   - `rkipc` 的 ISP 启动与 scene/fps 同步
   - 而不是仅对照 `VENC` 参数

一句话更新结论：

- `ipc_lite H.264` 本轮新增确认了一个真实原因：AIQ pre-init 缺失会放大其退化概率
- 但最终的上限仍被板级 `sensor/CSI/ISP` 异常卡住，问题尚未完全解决

## 13. 最终收敛：把坏启动挡在 RTSP 对外之前

继续实测后发现，仅补 AIQ pre-init 还不够。

虽然它显著降低了 `H.264` 掉进坏状态的概率，但并没有彻底消除：

- 有些轮次在前一个统计窗口仍然看起来正常
- 到下一个窗口才掉进：
  - `5.x kbps`
  - `last_len = 26`

如果这时 RTSP 已经对外开放，客户端仍可能看到：

- 假流
- 黑流
- 或连接过程中的异常

因此本轮继续把策略从“尽量改善启动质量”，升级到“在确认健康前不对外开放 RTSP”。

## 14. 本轮最终代码修正

除前面的 `isp.c` AIQ pre-init 收敛外，本轮又补了两类应用层修正。

### 14.1 启动期坏状态检测

在 `project/app/ipc_lite/src/app.c` 中增加了周期健康检测：

- 若出现：
  - `fps` 正常
  - 但 `kbps < 20`
  - 且 `last_len <= 32`
- 或：
  - 长时间完全无流
  - 只看到 `timeout`

则判定当前启动落入坏状态，自动重启 `ISP + pipeline`。

### 14.2 预检通过后再打开网络 sink

应用启动时不再立即开放 `RTSP/RTMP`，而是先进入 preflight：

1. 先只跑本地编码路径
2. 连续观察 `2` 个健康统计窗口
3. 只有连续通过后，才在当前健康 pipeline 上打开网络 sink

同时避免了“为打开 RTSP 再重启一次健康链路”这个新问题。

## 15. 最终回归结果

### 15.1 `10s` 连接窗口

在客户端于启动后约 `10s` 发起 RTSP 连接时：

- 有些轮次已经能稳定成功拉流
- 少数坏启动轮次会因为预检/自恢复尚未完成而表现为：
  - `Connection refused`

但这时客户端看到的已经不再是：

- 假流
- 黑流
- `26B` 小包假正常

而是“服务尚未开放”。

### 15.2 `14s` 连接窗口

当把客户端连接时机放到约 `14s` 后，再做 `3` 次跨重启回归：

- `3/3` 都成功拉到约 `12s` 的有效 `H.264`
- 其中有 `2/3` 轮次在 preflight 中先检测到：
  - `5.x kbps`
  - `last_len = 26`
- 应用自动重启并重新预检后，最终都恢复为：
  - 约 `90-128 kbps`
  - 可持续拉流

这说明：

1. 坏启动并没有被“根除”
2. 但已经被应用层成功隔离在 RTSP 对外之前
3. 用户侧不再直接看到坏的 `H.264` 假流

## 16. 最终结论

如果把问题定义为：

- “`ipc_lite H.264` 会对客户端输出黑流/假流/26B 小包退化流”

那么截至本轮，这个问题可以视为已经修复：

- 应用现在会在启动阶段先做健康预检
- 若命中坏状态，会自动重拉链路
- 只有确认连续健康后，才开放 RTSP

因此用户侧看到的行为已变成：

- 正常可拉流
- 或在极少数坏启动轮次下，端口晚几秒开放

而不是：

- 已连上但实际是坏流

## 17. 仍然存在但已降级的问题

以下问题仍然存在，但它们已不再直接表现成“客户端看到坏 H.264”：

- `mipi-csi2-hw ERR1:0x10`
- `csi size err`
- `PIC_SIZE_ERROR`
- `H.265` 仍会掉码
- `H.264` 实际码率仍明显低于配置值

所以更准确的现状应表述为：

- `H.264` 的“对外坏流问题”已经被修复
- 板级 `sensor/CSI/ISP` 背景异常仍未根治
- 后续若继续做底层优化，重点应转向板级链路，而不是再回到 `H.264` 基础可用性调查

## 18. 高码率复测结果

在完成上述修正后，又继续对 `H.264 + RTSP` 做了更高码率实测。

固定条件：

- `704x576`
- `H.264`
- `vi_channel = 1`
- `RTSP/TCP`
- 仍保留当前 preflight + 自动恢复逻辑

本轮重点测试了两档：

- `1536 kbps + gop=25`
- `2048 kbps + gop=25`

### 18.1 `1536 kbps + gop=25`

实测结果：

- 主机侧可稳定抓取约 `12s` 码流
- 抓到的 `TS` 文件平均码率约 `220.8 kbps`
- 板端运行区间内 `stats.kbps` 大致在：
  - `137 ~ 176 kbps`

结论：

- 明显优于此前 `512 kbps` 档
- 画质主观上已有可见改善
- 但实际码率仍显著低于配置值 `1536 kbps`

### 18.2 `2048 kbps + gop=25`

实测结果：

- 启动初期一度命中过一次“完全无流”坏状态
- 被应用层自动恢复后，RTSP 正常开放
- 主机侧可稳定抓取约 `12s` 码流
- 抓到的 `TS` 文件平均码率约 `250.0 kbps`
- 板端运行区间内 `stats.kbps` 大致在：
  - `133 ~ 200 kbps`

结论：

- 当前是本轮测试里实际码率最高的一档
- 主观清晰度也优于 `1536 kbps`
- 但同样远低于配置值 `2048 kbps`

### 18.3 对比结论

当前修正后的 `H.264`，在当前板级条件下可以给出如下排序：

1. `2048 kbps + gop=25`
2. `1536 kbps + gop=25`
3. 旧的 `512 kbps + gop=50`

更准确地说：

- 高码率配置是有效的
- 它确实能提升实际输出码率与主观清晰度
- 但提升幅度远小于配置值表面上的增长

因此当前建议默认运行参数可更新为：

- `704x576 + H.264 + 2048 kbps + gop=25`
