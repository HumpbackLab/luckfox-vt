# mis5001 0x3307 clock scalar 验证记录

日期：2026-04-18

## 1. 目标

验证 `MIS5001` 寄存器 `0x3307` 是否为 sensor 主时钟 / PLL scalar。

实验采用保守降频方式，不做升频：

- 基于已稳定的 `1280x720@60` sensor mode。
- 只把 `1280x720` mode 内的 `0x3307` 从 `0x84` 降到 `0x70`。
- 同步把 driver 暴露的 `MIS5001_LINK_FREQ` 从 `445500000` 改到
  `378000000`，使接收端按新的 MIPI lane rate 配置。
- 通过 CIF raw 抓帧验证实际帧周期是否按比例变化。

## 2. 背景推导

`mis5001.c` 原始配置：

```text
XVCLK = 27MHz
MIS5001_LINK_FREQ = 445.5MHz
MIPI data rate = 891Mbps
0x3307 = 0x84 = 132
HTS = 0x0BB8 = 3000
1280x720@60 VTS = 0x03DE = 990
```

已知 `1280x720@60` 的 timing clock：

```text
HTS * VTS * fps = 3000 * 990 * 60 = 178,200,000
```

把 `0x3307 = 0x84 = 132` 代入后，能得到：

```text
timing_clock = 27MHz * 132 / 20 = 178.2MHz
link_freq    = 27MHz * 132 / 8  = 445.5MHz
mipi_rate    = 27MHz * 132 / 4  = 891Mbps
```

同源驱动 `mis4001.c` 提供了对照：

```text
MIS4001_LINK_FREQ = 337.5MHz
0x3307 = 0x64 = 100
timing_clock = 27MHz * 100 / 20 = 135MHz
link_freq    = 27MHz * 100 / 8  = 337.5MHz
```

因此实验假设为：

```text
timing_clock = XVCLK * reg_0x3307 / 20
link_freq    = XVCLK * reg_0x3307 / 8
mipi_rate    = XVCLK * reg_0x3307 / 4
```

## 3. 实验改动

临时改动文件：

- `sysdrv/source/kernel/drivers/media/i2c/mis5001.c`

临时 diff：

```diff
-#define MIS5001_LINK_FREQ		445500000  //891Mbps  Mbps/2 = MHz
+#define MIS5001_LINK_FREQ		378000000  //756Mbps  Mbps/2 = MHz

 static const struct regval mis5001_linear_10_1280x720_regs[] = {
-	{0x3307, 0x84},
+	{0x3307, 0x70},
```

注意：

- 只改 `1280x720` mode 内的 `0x3307`。
- 早期 `2592x1944`、`1104x624`、`832x464` mode 的 `0x3307` 保持 `0x84`。
  2026-04-22 后当前实现统一改为 `1080Mbps/lane`，正式保留
  `1280x720@90` 与 `1920x1080@60`。
- 实验后本地源码已还原。

理论预测：

```text
0x70 = 112
112 / 132 = 0.848484...

new_timing_clock = 27MHz * 112 / 20 = 151.2MHz
new_link_freq    = 27MHz * 112 / 8  = 378.0MHz
new_mipi_rate    = 27MHz * 112 / 4  = 756Mbps

fps = 151.2MHz / (3000 * 990) = 50.909fps
frame interval = 1000 / 50.909 = 19.64ms
```

## 5. 实测结果

### 5.1 基线模块

部署实验模块前，原始稳定模块的 `1280x720` raw 结果：

```text
bytesused = 1290240
delta ~= 16.666ms
fps = 60.00
```

代表性输出：

```text
cap dqbuf: seq:  20 bytesused: 1290240 delta: 16.649 ms fps: 60.00
cap dqbuf: seq: 119 bytesused: 1290240 delta: 16.650 ms fps: 60.00
```

### 5.2 `0x3307 = 0x70` 降频模块

实验模块加载后，`1280x720` raw 结果：

```text
bytesused = 1290240
delta ~= 19.64ms
fps = 50.91
```

代表性输出：

```text
cap dqbuf: 1 seq:      4 bytesused: 1290240 ts: 29.421221 delta: 19.622 ms fps: 50.91
cap dqbuf: 2 seq:    119 bytesused: 1290240 ts: 31.680151 delta: 19.646 ms fps: 50.91
```

结果与理论预测完全一致。

检查 dmesg：

```text
未出现 fs/fe mis
未出现 csi size err
未出现 PIC_SIZE_ERROR
```

只看到正常的 stream on/off：

```text
rockchip-mipi-csi2 mipi0-csi2: stream ON
rockchip-mipi-csi2 mipi0-csi2: stream OFF
```

### 5.3 回滚确认

实验后将板端 `/oem/usr/ko/mis5001.ko.prev` 复制回
`/oem/usr/ko/mis5001.ko` 并重启。

回滚后再次短抓 `1280x720` raw：

```text
delta ~= 16.666ms
fps = 60.00
```

代表性输出：

```text
cap dqbuf: 2 seq: 29 bytesused: 1290240 ts: 30.415514 delta: 16.666 ms fps: 60.00
```

## 6. 结论

`0x3307` 可以确认是 `MIS5001` 当前寄存器表里的主 clock scalar。

当前可采用公式：

```text
timing_clock = XVCLK * reg_0x3307 / 20
link_freq    = XVCLK * reg_0x3307 / 8
mipi_rate    = XVCLK * reg_0x3307 / 4
```

对当前默认值：

```text
0x3307 = 0x84 = 132
timing_clock = 178.2MHz
link_freq = 445.5MHz
mipi_rate = 891Mbps
```

对本次实验值：

```text
0x3307 = 0x70 = 112
timing_clock = 151.2MHz
link_freq = 378.0MHz
mipi_rate = 756Mbps
```

因此后续如果要尝试升频，应同步处理：

- sensor mode 内 `0x3307`
- driver `MIS5001_LINK_FREQ`
- V4L2 `V4L2_CID_PIXEL_RATE`
- mode 的 `max_fps` / `vts_def` 设计
- 板端 CSI 错误检查：`fs/fe mis`、`csi size err`、`PIC_SIZE_ERROR`

## 7. 后续建议

升频应按小步推进，不建议直接大幅跳变。

候选值：

```text
0x88 = 136 -> timing_clock 183.6MHz, link_freq 459.0MHz, mipi_rate 918Mbps
0x8C = 140 -> timing_clock 189.0MHz, link_freq 472.5MHz, mipi_rate 945Mbps
0x90 = 144 -> timing_clock 194.4MHz, link_freq 486.0MHz, mipi_rate 972Mbps
```

每一步都应先跑 CIF raw，确认：

- 连续 DQBUF 稳定
- frame interval 符合预测
- dmesg 无 CSI 错误
- 再进入 ISP/selfpath、VENC、UDP/RTSP 链路验证

另一个待验证点是 `0x3308`：

- `mis4001` 中 `0x3308 = 0x03`
- `mis5001` 中 `0x3308 = 0x04`

它可能是 PLL range / band / charge-pump 类配套参数，不直接进入线性公式。
如果后续 `0x3307` 升高后 CSI 或 sensor 不稳定，可以尝试查找或扫描
`0x3308` 的安全取值，但应作为独立实验处理。
