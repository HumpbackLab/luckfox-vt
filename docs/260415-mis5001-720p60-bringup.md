# mis5001 720p60 Bring-up 记录

日期：2026-04-15

## 1. 目标

把 `mis5001` 从当前默认的 `2592x1944@25` 路径，扩展出一条可用于 `ipc_lite` 的：

- `1280x720`
- 原生 sensor mode
- 目标 `60fps`
- `rkisp_selfpath + H.264 + RTSP`

这次工作的重点不是“单纯把 `ipc_lite.ini` 改成 60”，而是把整条链路真正打通：

1. sensor 侧增加原生 `1280x720` mode
2. 启动时显式选中新 mode
3. IQ 文件补齐 `1280x720` 对应项
4. 用实测结果反推并修正 mode 时序

## 2. 代码与配置改动

### 2.1 `mis5001` 新增 `1280x720` mode

修改文件：

- [sysdrv/source/kernel/drivers/media/i2c/mis5001.c](/home/ncer/luckfox-vt/sysdrv/source/kernel/drivers/media/i2c/mis5001.c:355)

新增：

- `mis5001_linear_10_1280x720_regs[]`
- `supported_modes[]` 里的 `1280x720` 项

模式设计思路：

- 保持 `HTS = 0x0BB8`
- 基于 `2592x1944` 做中心裁剪
- ROI:
  - `x_start/x_end = 0x0290 / 0x078F`
  - `y_start/y_end = 0x0264 / 0x0535`
- 输出尺寸寄存器 `0x4224 ~ 0x4233` 全部改成 `1280x720`

最终保留的 `VTS`：

- `VTS = 0x03DE`

说明：

- 最初尝试用 `VTS = 0x0339` 作为 `60fps` 目标值
- 实测发现实际输出约 `72fps`
- 后续根据板上真实输出反推，修正为 `0x03DE`

### 2.2 `ipc_lite` 新增 720p60 配置

新增文件：

- [project/app/ipc_lite/ipc_lite.720p60.lowlat.rtsp.ini](/home/ncer/luckfox-vt/project/app/ipc_lite/ipc_lite.720p60.lowlat.rtsp.ini:1)

主要参数：

- `codec = h264`
- `vi_channel = 1`
- `venc_channel = 1`
- `venc_buffer_count = 2`
- `venc_buffer_size = 1382400`
- `venc_timeout_ms = 200`
- `sync_sensor_fps = true`

板端默认配置已切到这份 720p60 版本。

### 2.3 `run.sh` 增加启动前强制选 mode

修改文件：

- [project/app/ipc_lite/run.sh](/home/ncer/luckfox-vt/project/app/ipc_lite/run.sh:1)

新增逻辑：

- 从 `-c` 指定的 ini 里读取 `[video] width/height`
- 启动 `ipc_lite` 前先执行：

```sh
media-ctl -d /dev/media0 \
  --set-v4l2 "'m00_b_mis5001 4-0031':0[fmt:SGRBG10_1X10/${width}x${height}]"
```

原因：

- 仅在 `mis5001.c` 里加新 mode 不够
- `ipc_lite` 默认只会把 ISP/VI 输出设成 `1280x720`
- 不会自动把 sensor subdev 切到新 mode
- 如果不显式 `media-ctl`，实际仍是：
  - sensor: `2592x1944@25`
  - selfpath: 缩成 `1280x720`

### 2.4 IQ 文件补 `1280x720` 的 ALSC 项

修改文件：

- [media/isp/release_camera_engine_rkaiq_rv1106_arm-rockchip830-linux-uclibcgnueabihf/isp_iqfiles/mis5001_CMK-OT2115-PC1_30IRC-F16.json](/home/ncer/luckfox-vt/media/isp/release_camera_engine_rkaiq_rv1106_arm-rockchip830-linux-uclibcgnueabihf/isp_iqfiles/mis5001_CMK-OT2115-PC1_30IRC-F16.json:1)

背景：

- 启动 `720p` 后 AIQ 报：
  - `ALSC:E: can't find 1280x720 in lscResName`

本次做的是功能验证级修法，不是重新标定：

- 在 `resolutionAll` 里新增 `1280x720`
- 复制现有 `2592x1944_*` 的 ALSC 表
- 生成对应的 `1280x720_*` 条目

结果：

- 启动后不再出现 `can't find 1280x720 in lscResName`
- 但这仍然只是“复用高分辨率 LSC”，不是正式标定结果

## 3. 板上验证过程

### 3.1 初始现象：`ini=60` 但实际仍只有 25fps

最早的问题不是 `ini` 没生效，而是 sensor mode 没切过去。

验证结果：

- `ipc_lite` 日志读到了 `fps=60`
- `isp` 也打印了 `sensor fps fixed to 60`
- 但同一时刻仍显示：
  - `sensor raw width : 2592`
  - `sensor raw height : 1944`
- 实际统计依然只有 `23 ~ 25 fps`

结论：

- 这时跑的是 `2592x1944@25` 的 sensor
- `1280x720` 只是 ISP `selfpath` 的输出尺寸

### 3.2 `media-ctl` 强制切 mode 后，sensor 变成原生 720p

在板上手动执行：

```sh
media-ctl -d /dev/media0 \
  --set-v4l2 "'m00_b_mis5001 4-0031':0[fmt:SGRBG10_1X10/1280x720]"
```

之后可见：

- `sensor raw width : 1280`
- `sensor raw height : 720`
- subdev 控制项变成新 mode 的时序参数

这证明：

- sensor mode 本身是可被选中的
- 问题在于启动流程没有自动选中它

## 4. `70+ fps` 和大延迟的定位

### 4.1 先排除错误方向

最初怀疑过：

- `ipc_lite` 是否把一个 `VENC` frame 的多个 pack 当成多帧

为确认这件事，临时给 `ipc_lite` 做过只读诊断埋点，记录：

- `u32PackCount`
- `u32Len`
- `u32Offset`
- `u64PTS`
- `bFrameEnd`

这部分诊断代码没有保留在仓库，也没有保留在板端当前版本中。

### 4.2 诊断结果

实测发现：

- `pack_count = 1`
- `bFrameEnd = 1`
- 不是“一帧多包”

也就是说：

- `70+ fps` 不是统计假象
- 编码器确实在按大约 `72fps` 输出完整访问单元

### 4.3 真正根因

问题不在 `ipc_lite`，而在最初新加的 sensor mode 时序不对。

当时使用：

- `VTS = 0x0339`

实测结果：

- `stats fps` 稳定在 `71 ~ 72`
- 同时一直能看到：
  - `VVI_IOCTL_SET_FR ioctl fail`

结论：

- `VI` 侧限帧并没有真正生效
- sensor 实际输出又高于目标 `60fps`
- 下游只能积压，表现为明显大延迟

## 5. 用实测反推修正 `VTS`

已知：

- 初始 `VTS = 0x0339 = 825`
- 实际输出约 `72fps`
- 目标 `60fps`

按比例反推：

```text
VTS_new ≈ 825 * 72 / 60 ≈ 990 ≈ 0x03DE
```

于是把新 mode 改成：

- `VTS = 0x03DE`

并重新：

1. 编译 `mis5001.ko`
2. 上传到板子
3. 用 `project/scripts/mis5001-dev.sh reboot-reload` 重启激活

说明：

- 这块板上 `mis5001` 热卸载不稳定
- 实际最稳妥的模块更新方式仍然是：
  - `build`
  - `deploy`
  - `reboot-reload`

## 6. 最终实测结果

更新后的板上原版 `ipc_lite` 实测：

- `sensor raw width : 1280`
- `sensor raw height : 720`
- `sensor fps fixed to 60`
- `stats fps` 稳定在：
  - `57.8`
  - `59.7`
  - `59.9`
  - `60.8`

结论：

- 当前 `mis5001 1280x720` mode 已从“误跑到 72fps”修正到“真实接近 60fps”
- 此前的“大延迟”主因就是 sensor 侧时序失配，而不是 `ipc_lite` 统计口径错误

## 7. 当前板端状态

当前板端已经生效的内容：

- `run.sh` 启动前自动 `media-ctl` 切 mode
- IQ 文件里已补 `1280x720` ALSC 条目

当前板端未保留的内容：

## 8. 已知剩余问题

即便 `fps` 已经回到真实 `60`，日志里仍然有：

- `VVI_IOCTL_SET_FR ioctl fail`

这说明：

- `ipc_lite` 的 `VI` 帧率设置路径本身并不可靠
- 当前之所以输出正常，主要靠的是 sensor mode 自身已经跑到接近目标 `60fps`

此外还需要注意：

- `1280x720` 的 ALSC 目前只是复用了 `2592x1944` 的表
- 能做功能验证，不等于正式量产标定

## 9. 建议的后续工作

1. 做一次真实 RTSP 端到端观看验证，确认延迟相较旧版是否明显下降
2. 若仍有明显延迟，再转向排查：
   - RTSP 客户端缓存
   - `rtsp_demo` 队列
   - `ipc_lite` 的启动前 `preflight` 窗口
3. 若计划长期保留 `720p60`，建议后续补真正的 `1280x720` LSC 标定
