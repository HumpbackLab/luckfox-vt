# mis5001 90fps / 120fps 配置记录

日期：2026-04-17

更新：2026-04-22 已将当前正式实现切到 `1280x720@90` 和
`1920x1080@60`。本文中的 `1104x624` 配置保留为历史调试记录，当前
driver / `ipc_lite` 安装清单已不再暴露 `1104x624` mode 或对应 ini。
新的实现记录见 `docs/260422-mis5001-720p90-1080p60.md`。

## 1. 目标

在现有 `1280x720@60` mode 基础上，继续增加两条高帧率验证配置。
初版按 `720p60` 的 VTS 比例得到 `848x480@90` 和 `640x360@120`；
后续按 `4M@30` 吞吐上限尝试继续提高分辨率；实测发现
`1536x864@90` 这类需要降低 HTS 的配置会触发 CSI `fs/fe mis`，
因此当前稳定方向是固定 `HTS=0x0BB8`，在各帧率 VTS 内尽量提高 active height。

- `1104x624@90`
- `832x464@120`

这两条配置仍按 `rkisp_selfpath + H.264 + UDP/RTP` 的低延迟验证路径设计。

## 2. 分辨率与时序推导

当前提高分辨率按 `4M@30` 作为吞吐约束：

基础值：

```text
4M@30 = 4,000,000 * 30 = 120,000,000 pixel/s
MIS5001 当前 30fps 时序基准 = HTS 3000 * VTS 1980 * 30
                         = 178,200,000 timing clocks/s
```

### 2.1 90fps

```text
max_active_pixels_90 = 120,000,000 / 90 = 1,333,333
1104 * 624 = 688,896
1104 * 624 * 90 = 62,069,760 pixel/s
```

取 16:9 且 16 对齐：

```text
1104x624
```

固定 HTS，按 90fps 设置 VTS，并保留 36 行 vertical blank：

```text
HTS = 3000 = 0x0BB8
VTS = 660  = 0x0294
fps = 178,200,000 / (3000 * 660) = 90.0
vertical blank = 660 - 624 = 36
```

`MIS5001` 这里的垂直 end 坐标不是普通 inclusive 公式；按现有
`2592x1944` 和 `1280x720` 表反推，实际高度为 `y_end - y_start - 1`。
所以 `y_end` 要按 `y_start + height + 1` 算。

```text
x_start = (2592 - 1104) / 2 = 744   = 0x02E8
x_end   = 744 + 1104 - 1    = 1847  = 0x0737
y_start = (1944 - 624) / 2  = 660   = 0x0294
y_end   = 660 + 624 + 1     = 1285  = 0x0505
```

### 2.2 120fps

```text
max_active_pixels_120 = 120,000,000 / 120 = 1,000,000
832 * 464 = 386,048
832 * 464 * 120 = 46,325,760 pixel/s
```

取接近 16:9 且 16 对齐：

```text
832x464
```

固定 HTS，按实测 `848x480` 只能到约 `115fps` 的结果，继续降低 VTS
到 `0x01D6`，并保留 6 行 vertical blank：

```text
HTS = 3000 = 0x0BB8
VTS = 470  = 0x01D6
fps ~= 120
vertical blank = 470 - 464 = 6
```

居中 ROI：

```text
x_start = (2592 - 832) / 2 = 880  = 0x0370
x_end   = 880 + 832 - 1    = 1711 = 0x06AF
y_start = (1944 - 464) / 2 = 740  = 0x02E4
y_end   = 740 + 464 + 1    = 1205 = 0x04B5
```

## 4. 注意

当前 IQ 只是功能验证级补齐，避免 AIQ 因找不到 resolution 报错；它不是针对 `1104x624` 或 `832x464` 重新标定的正式 LSC。

高帧率验证需要分开看三条链路：

- CIF raw：只验证 sensor + CSI 是否能按新 mode 出帧。
- `v4l2_mpi_venc_probe`：走 V4L2 + MPI VENC，不走 RK_MPI_VI，但仍会受 ISP/selfpath 和串行编码/发送链路影响。
- `ipc_lite`：走完整 `rkisp_selfpath + RK_MPI_VI + VENC + UDP/RTP` 链路。

不要只用 probe 或 `ipc_lite` 的最终 fps 反推 sensor fps。90fps 帧周期只有 `11.11ms`，120fps 帧周期只有 `8.33ms`；如果取帧、送编码、等码流、UDP 发送在一个线程内串行执行，单帧处理时间接近或超过帧周期后，V4L2/ISP 侧就可能开始排队，表现为 `age` 增大、最终统计 fps 低于 sensor raw fps。

## 5. 板端验证结果

初版验证发现之前按 inclusive 公式写 `y_end` 时，CSI 实际收到：

- `848x480` -> `848x478`
- `640x360` -> `640x358`

修正 `y_end` 后，直接走 CIF raw 抓帧验证通过：

- `848x480`: `v4l2-ctl` 连续 60 帧，帧间隔约 `11.11ms`，稳定 `90fps`
- `640x360`: `v4l2-ctl` 连续 60 帧，帧间隔约 `8.33ms`，稳定 `120fps`

`ipc_lite + rkisp_selfpath` 验证：

- `848x480@90`: UDP/H.264 正常出流，统计约 `89.8-90.8fps`
- `640x360@120`: sensor/CIF raw 正常，但 ISP mainpath/selfpath 均未出编码帧，需继续查 ISP/VI 链路限制

按 `4M@30` 尝试继续提高分辨率后的验证结果如下。

### 5.1 失败尝试：降低 HTS 提高 active height

尝试过更接近 `4M@30` 上限的配置：

- `1536x864@90`
- `1328x752@120`

这类配置需要把 HTS 从 `0x0BB8` 明显降低。板端现象是 `STREAMON` 能成功，但没有稳定 `DQBUF`，内核日志持续出现：

```text
mipi-csi2-hw ERR1:0x10 (fs/fe mis,vc: 0)
```

因此当前结论是：不能只按 pixel throughput 把 HTS 压低来换更大 active window；至少这组寄存器路径下，CSI 帧起止同步会失败。

### 5.2 当前较稳方案：固定 HTS=0x0BB8

`1104x624@90`：

- CIF raw 抓帧通过。
- `v4l2-ctl` 连续 90 帧，`bytesused=958464`。
- 帧间隔约 `11.111ms`。
- 统计稳定 `90.00fps`。
- 验证后 `mis5001` 日志无连续 `fs/fe mis`。

`832x464@120`：

- CIF raw 抓帧通过。
- `v4l2-ctl` 连续抓帧，`bytesused=593920`。
- 帧间隔约 `8.417ms`。
- 实测约 `118.80fps`。
- VTS 从 `0x01DB` 继续压到 `0x01D6` 后，raw fps 没有继续明显提升，疑似 sensor 内部或链路存在最小 timing/blanking 限制。

`v4l2_mpi_venc_probe` 在 `832x464@120` 上的阶段性结果：

- 命令使用 `/dev/video12`，`pixfmt=nv12`，`-n 240 -b 3`。
- probe 能启动 AIQ、V4L2、MPI VENC，并正常 UDP 输出 H.264。
- summary 约 `fps=89.23`。
- 平均 `age` 约 `12.955ms`，最大约 `20.637ms`。
- `sink` 最大约 `10.640ms`，已经接近 90fps 单帧周期。

这个结果更像是 probe 当前串行链路把 V4L2/ISP 输出压住了，不等同于 sensor raw 只有 89fps。后续如果要用 probe 验证 120fps，需要把取帧、编码输出、UDP 发送拆开，或先关闭 UDP sink/drain 编码输出，单独测各阶段吞吐。
